# Onboarding, Authorization, and Secure Login

## 1. Capabilities and Website Selection
Discover tools first rather than assuming that “your own computer” stays online permanently. Verify cloud browser control and session persistence; Library/other persistent file storage; Excel editing; real recurring scheduling; notifications back to the original conversation; and an optional connected user computer. Read the tool instructions. If only a local browser is available, explain that collection cannot continue while the computer is off, and obtain the user's agreement before switching to local mode. Without a scheduler, offer manual operation only; waiting during the current turn is not an ongoing service.

Ask “Which website would you like to track? You can give me an existing cart link.” Resolve the official source and open the target cart through the normal UI. Check the regional site, currency, and account context; do not silently replace the Chinese site with an international one. Prefer the currently authorized cloud session and do not arbitrarily switch accounts. Assign separate dataset_id values to different sites and accounts. Access only through methods permitted by current tools; APIs are not a back door around the UI or an access refusal.

## 2. One Low-Friction Confirmation
When information is missing, bundle the question:
> By default, I will capture every 4 hours (measured as elapsed time from the activation anchor; you can choose daily or fixed local times instead), following your verifiable timezone automatically. First show the detected timezone and its source; if uncertain, ask only for the timezone. May I save cart price/promotion history in the cloud, temporarily select individual items and specified combinations, and then restore the original selection? I will not change quantities, claim coupons, or buy anything. Initially, I will create data/image folders under Price tracking on your desktop; data will be written there only when you request synchronization. Shall I use these settings?
Also identify the cloud service being used: cloud processing means data leaves the local computer and is processed/stored by the current service. Do not simultaneously promise that “nothing is uploaded to any server.” If the user requires local-only processing, adjust the architecture and explain gaps during power-off periods; do not silently change the privacy boundary.

Combinations are optional:
> Are there any items you especially want to buy together? Names or links are enough—for example, “电脑套装：显示器+键盘” (“Computer setup: monitor + keyboard”). If you are unsure, I can start with individual items and estimate other combinations later.
Echo back the cart's verified identity (SKU or an alternative identifier for a confirmed single-variant product), specifications, and original quantity to resolve ambiguity. When one name matches multiple SKUs, ask only about the key difference; do not choose specifications for the user. If the requested quantity differs from the original cart quantity, do not change it unilaterally; record at the current quantity or ask whether separate authorization is intended. Save combination versions and effective times; deactivation does not delete earlier definitions.

By default, suggest a reminder every 3 days asking “Would you like to see trend charts?” (Chinese alias: “要不要看趋势图？”), without requiring enough new data. Explain and confirm initially; it can be disabled at any time. Deduplicate by period, and do not permanently stop agreed reminders merely because the previous one went unanswered. By default, after new charts pass verification, move only this skill's old charts to the Recycle Bin/Trash. Explain this initially and obtain authorization for that scope.

## 3. Optional grill-me (Fill Only Critical Gaps)
If the user wants a deeper refinement, use two rounds with no more than three questions per round, skipping answers already known:
1. Which site/account scope should be tracked? Which region, membership, or channel affects quotes? What granularity of anonymized context may be saved?
2. Should single-item curves show the total at the original quantity or the unit price (default: both, clearly labeled)? Which actual combinations matter?
3. What price-drop threshold/quiet hours apply? Report every run or only exceptions? How often should chart reminders appear?
4. May local synchronization update the skill's own same-named files? What is the old-chart recycling policy? What cloud capacity/history-retention constraints apply?
Do not block the first trial for nonessential preferences. Without an answer about thresholds, do not invent an alert criterion for a “significant price drop”; objectively report the difference instead.

## 4. Login Paths
- **Existing session:** List normal tabs again, then navigate to/locate the cart. Check whether actual products or an explicit empty-cart state appear, as well as login state; an avatar or the user's statement alone is insufficient.
- **QR code:** Open the official login method and have the user scan with the official mobile app; explain that this is the same cloud browser. Do not persist the QR code. After the user finishes, close stale prompts/cancel stale authentication requests according to tool instructions, then refresh the actual page once to verify.
- **Username and password:** Use the tool-supported secure handoff so the user enters and submits credentials in the official fields or a supported password manager. Do not ask for credentials in chat, logs, or configuration, and do not read password stores or browser storage yourself. Continue with actual UI verification after authentication.
- **SMS verification code:** Have the user request and securely enter the code for this website's current login session. If the tool supports only secure authentication handoff, use that handoff. Do not request codes whose connection to this attempt is unclear, save/forward them, or repeatedly trigger SMS messages. Follow tool rules if sending a code requires user confirmation.
- **Second-factor verification/device confirmation:** Wait for the user to complete the official action; do not simulate success. If the current tool does not support a passkey, explain that the user can choose another normal website-provided method they are willing to use; do not claim it has been handled.
- **Account switching:** Require confirmation of the target to avoid reading another account. Switching accounts creates a separate context/dataset; do not silently append it to the old history.

If the user says “已登录” (“I'm logged in”) but a login overlay remains: confirm the same environment → list tabs again → inspect the actual page → perform one normal refresh → check products/identity state → if successful, cancel the stale authentication wait. If it still fails, describe the specific on-screen state and minimum necessary action. Do not ask the user to repeat login indefinitely.

## 5. File Initialization and First-Run Acceptance
Save configuration in permission-protected persistent storage, containing only file identities, task identities, and anonymous context—not credentials. Create 19 logical tables; tables without data may remain empty. When migrating an existing ledger, first map its fields and versions; do not create a second master workbook.
Perform one real trial capture. Show a few anonymized examples, total item count/completeness, successful single-item quote count, collected promotions and missing fields, time/amount semantics, selection-restoration verification, and save results. Ask the user to confirm before formal activation. If declined or not approved, leave the schedule inactive; this does not affect the safely saved facts from the trial.

## 6. Handover and Minimal Repeated Actions
When another dot takes over, first verify the current user's access rights and valid authorization for the dataset, cloud files, and task. Read persistent configuration, versions, unfinished commits, and existing schedules; reuse the same master workbook/task. Do not copy passwords, Cookies, or other people's sessions. A currently accessible login session may be verified and continued; installing the skill does not confer another user's authorization. Account changes require isolation; if the account is unknown, pause the relevant reads.
Initially explain frequency, timezone source/policy, next scheduled occurrence, three-day chart reminders, and selection boundaries together. Defaults are not authorization. Adopt the user's existing explicit choices directly; ask only about permissions and necessary configuration that cannot be inferred. If the user requests daily collection without specifying a time, suggest 10:00 local time in the same bundled confirmation rather than silently selecting a time.
