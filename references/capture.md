# Normal-UI collection for each run

## A. Start and refresh
1. Read this run's scheduled time, configuration, latest user restrictions, and combination definitions; acquire the dataset's exclusive lock. If the same run is already committed, return its status without repeating operations. First download the latest authoritative Excel/JSON and their version numbers.
2. Locate the target site through the current tool's normal tab list; do not reuse old tab IDs. Confirm that neither the user nor another run is operating concurrently. Stop and report any outside interaction; do not compete with the user for control.
3. Check the official domain, regional site, and login state. Follow the authentication reference if login is necessary; do not attempt to evade CAPTCHAs or security refusals.
4. **Perform one normal refresh/reload of the cart in every run**, recording refresh_started_at, refresh_completed_at, and refresh_status. Wait for loading overlays/skeletons to disappear, the product area to appear, and asynchronous prices to stabilize. Require at least two normal UI observations with consistent items/totals and no loading indicator; include each observation's time in the evidence. Network idle alone does not prove that prices have updated.
5. If refresh fails or redirects to login, stop the affected quotations and record failure. Do not present the previous run's cache as current data. After refresh, inspect the original selection set, original quantities, and the minimum necessary account/region/membership/channel context. Do not repeatedly refresh without a limit in pursuit of “updated prices.”

## B. Full-cart baseline and coverage
6. Scroll section by section from top to bottom, handling normal pagination/load-more controls. Collect visible entries in each section before scrolling; do not assume the DOM contains the entire list. Deduplicate using SKU/entry identifiers, not product names; the same SKU may occur in different shops or cart rows, requiring row_key.
7. Collect every entry, including invalid, delisted, out-of-stock, and unselectable entries. Record identity and evidence under the storage contract's three identity_status values (without inventing confidence probabilities), title, link, shop, specifications, quantity, visible price text and semantics, stock, selection state, and observation time. Leave undisplayed list prices, shipping fees, and stock counts empty; do not automatically interpret a struck-through number as the “original/list price.”
8. Continue to the bottom and verify the bottom/no further entries; return to the top if necessary to cross-check the product count and visible group count. Record reported_line_count, observed_unique_line_count, total_quantity, selectable_count, coverage_status, and coverage evidence. The site's “件数” (item count) may mean rows or units; mark its semantics unknown if unclear. Record 0 only for an explicitly empty-cart page; failure is null.
9. Safely expand collapsed groups, invalid-item sections, and promotion details in read-only fashion, without changing cart contents or claiming coupons. Mark inaccessible sections as uncovered and the run PARTIAL; do not call uncertain coverage complete.
10. Save the whole-cart baseline separately from the current-selection summary. The bottom total covers only the selected set; 0 with nothing selected is not the whole cart's value. Name any arithmetic sum of available item display prices derived_displayed_sum, not a payable amount.

## C. Promotion and eligibility evidence
11. Read visible promotions and details for every product, shop, and platform area: spend-and-save, savings for each threshold reached, multi-item discounts, cross-store campaigns, subsidies, coupons, and special combination prices. Save the original wording even when the threshold is unmet. Identical text does not automatically identify the same campaign; use scope + actual campaign identifier + version, or a run-local observation_id if no real identifier is available.
12. Extract only rule fields supported by evidence: threshold amount/quantity/unit, calculation basis (before/after discounts), reduction/discount rate, whether each threshold repeats, cap, maximum uses, validity including timezone, participating shops/SKUs/exclusions, quantity restrictions, eligibility/membership/channel, stacking/exclusion, and order. Mark each unknown field Unknown; do not fill gaps from general assumptions.
13. Save whether a coupon is claimed, claimable, applicable, its usage count, validity, scope, and conditions requiring it to be claimed first. Preserve labels such as “领券结算” (claim a coupon and check out) and “可享” (may be eligible for) verbatim; they do not prove that a coupon has been claimed or its conditions met. Record buttons without clicking to claim or check out.
14. Save only relevant, redacted text/structured evidence. Avoid full-page screenshots containing names, addresses, or account details. If the tool internally requires screenshots for operation, do not store full-page screenshots in the history. Evidence includes the page URL (with credential/tracking parameters removed), region of the page, time, and text.

## D. Single-item selected quotations
15. Before changing selections, confirm selection authorization for this run; record the original selected row_key set and each row's original quantity. Prepare a restoration checklist. Without authorization, collect only the baseline; do not record an unavailable quotation as 0.
16. Clear the selection to an empty set, locating each action semantically from newly read UI. Verify that the selection set is truly empty. Never click blindly using stale AX indices, fixed coordinates, or fragile old selectors.
17. Iterate over each selectable row_key; do not merge multiple rows of the same SKU. Preserve the original row multiplicity and each row's quantity. For each row: read the latest UI → select only that row → verify that the set contains exactly that row and its quantity is unchanged → wait for prices to stabilize → record the single quote's item subtotal, campaign/shop/platform reductions, delivery fee if explicit, selected-cart total, unit/row count, coupon conditions/button wording, context, and actual time → deselect → verify the empty set.
18. Label the quotation “cart quotation with one item selected (original quantity).” If the total includes surcharges, do not simply divide by quantity and call it the product unit price. If the product amount can be separated, record the formula and precision of any derived unit price. Do not call it an actual transaction/payment price, or treat a discount promised “after checkout” as already applied.
19. If the price after selecting an item differs from the baseline, keep both independent observations with their times and phases. Do not overwrite the baseline or claim simultaneity. A run spans a time window; it is not an atomic snapshot.

## E. Named combination quotations
20. Process only active combinations explicitly specified by the user and unambiguously mapped to current cart rows/identity versions (a verified single-variant product does not require a non-null SKU). A current row with unresolved identity may still be explicitly authorized by the user for an observed quote and stored as row-level facts; this does not establish an unsupported mapping across time. Do not enumerate every combination or add combinations on the user's behalf. Leave ComboQuotes empty when no combinations are specified.
21. Deselect everything → select each combination member → verify the exact set and original quantities → wait for stability → record the combination total, displayed discount allocations/rules, per-row amounts/quantities/eligibility, original text, time, and context → deselect. If quantities mismatch or an item is missing/unselectable, record that the combination cannot be measured; do not substitute SKUs or shrink the combination without authorization.
22. Do not treat the sum of individual quotations as an observed combination quote. Claiming requirements, cross-store thresholds, and stacking conditions may all change the result.

## F. Restore, validate, and finish
23. Restore the original selected set in a finally path, unless the user has explicitly specified a different final set (for example, leave all unchecked); record both baseline and authorized restoration target. Use the latest UI, verify every row's selection and quantity, and compare with the baseline. If selectability changes, record the difference rather than risking content changes to restore it. If an unexpected “删除/移到收藏” (delete/move to favorites) or similar dialog appears, cancel rather than confirm only when the cancel/close button is clearly identifiable, then re-verify the cart. If an unfamiliar dialog's button semantics cannot be confirmed, stop UI actions and report it; do not click unknown buttons blindly.
24. If restoration fails, immediately stop further selection changes and clearly report the unrestored rows and current state. Do not continue into another run that changes selections. At the next run, first confirm/safely restore the state.
25. If the user intervenes during the run, do not forcibly restore over their new selections. Stop, report that restoration is unverified, describe the original set and observed conflict, and wait for the user's clarification before proceeding.
26. Validate references, quantities, amounts, coverage, timestamps, and comparable differences; append under the storage protocol. Briefly report the actual Beijing time or user-local time, total cart entries and successful quotation count, major comparable price/promotion changes, Excel status, anomalies, and restoration result. Report failures honestly; never silently erase them at the next run.

## Identity and disappearing entries
An empty SKU is not grounds to skip collection. First save the current row, link, specifications, quantity, original text, and quotation, then classify it as VERIFIED_SINGLE_VARIANT or UNRESOLVED_VARIANT under the storage contract. The latter blocks only the affected strict cross-period comparisons/rule mappings, not other products. A current row must be unambiguously locatable for selection; otherwise preserve its baseline and skip selecting that row.
For a product present last run but absent now, record NOT_PRESENT_IN_CART only with complete coverage and a valid login (do not infer user deletion, delisting, or sell-out). Record delisted/out-of-stock status only when explicitly shown. Distinguish PARTIAL, login failure, and an explicitly empty cart. Do not fill disappearances with zero prices or delete history. Record reappearances and identity-mapping evidence.

## JD mobile-web route and selection rollback
For JD, prefer the normal mobile website https://m.jd.com/ and its visible shopping-cart entry. A known cart destination is https://mtrade.jd.hk/cart/cart.action; navigate normally and verify the current redirect/page rather than assuming permanent URL behavior. The desktop https://cart.jd.com/cart_index remains a source when accessible, not a prerequisite. Switching a compatible normal UI due to a functional selection problem is allowed within existing scope; never use the route to evade an access/security refusal.
Confirm the intended account, currency, delivery context, and cart section. JD may separate regular shopping (购物) and instant delivery (秒送); record sections and counts dynamically, never hard-code prior counts. “Entire cart” requires coverage of every authorized visible section or explicit PARTIAL coverage. Do not silently drop instant delivery, add its items to regular combinations, or change delivery locations. If the scope is ambiguous, collect safe baseline evidence and ask the single essential scope question before mutations.
Before bulk toggling, use one authorized row to verify select → stable quote → deselect → empty-set behavior, preserving its original quantity and the restoration target. If a fresh UI observation shows selection reverting, deselection failing, or a page re-render invalidating targets, stop the quote loop immediately. Distinguish loading/skeleton rebuild from actual navigation using normal UI evidence; do not guess the root cause or repeatedly toggle stale targets. Save successful observations, failing action/time, actual selection, and unresolved restoration status. Safely restore through the current supported UI when possible; otherwise stop mutations and request the smallest authorized manual correction. If the user clears selections on their phone, refresh and verify the cloud cart's actual empty set, not merely the phone report. Empty-set verification does not establish that the underlying selection bug is fixed: require a new controlled test before resuming. Do not overwrite concurrent user interaction.
