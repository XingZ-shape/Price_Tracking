# On-Demand Charts and Synchronization to the User's Desktop

## Local Directories: The Actual User Computer Is Required
On first adopting this skill, resolve the system's Desktop known-folder/API on the user's authorized connected computer (including OneDrive/redirection on Windows, and the actual desktop configuration on macOS/Linux). Do not guess `C:\Users\用户名\Desktop` (where 用户名 means username), and do not create a cloud Desktop and claim success. If multiple devices are connected, select one once.
Safely create `Price tracking/data` and `Price tracking/image` without deleting existing contents. If a same-named directory contains user files, preserve them and manage only the skill's own files registered in the manifest. Reject path traversal and out-of-bounds symlinks. Create a hidden or unobtrusive `.price-tracking-manifest.json` containing dataset_id, relative file paths, roles, hashes, cloud versions, owner, and creation times. Populate resolved_local_root in the configuration only after successful local verification.
If the user's computer is offline or permissions are insufficient, record PENDING_LOCAL_SETUP/PENDING_SYNC and continue authorized cloud collection. State the missing connection/write permission; do not claim that directories have been created or synchronization has succeeded.

## Data Synchronization (Only on Explicit Request)
“数据同步到我的本地” (“sync the data to my local computer”), “renew”, and “更新本地 Excel” (“update local Excel”) trigger synchronization; do not write locally every day by default. Use the verified Desktop/Price tracking/data destination. If the user specifies another location, update the configuration and use the latest explicit destination.
1. Obtain the latest COMMITTED cloud master workbook and source-data versions; verify they are not temporary or partially committed. Do not use inconsistent files from an in-progress, uncommitted run.
2. Compare the local manifest hash. If the user has edited the previously synchronized file, do not silently overwrite it: preserve it, write a separate new cloud copy with a short conflict suffix, and report that a user decision is needed. Do not unilaterally merge user edits into the authoritative cloud data.
3. Download to a temporary file on the destination filesystem. Reopen and verify all sheets, row counts, latest run, amounts, and timestamps; then atomically update the skill-owned `价格历史.xlsx` (“Price history”; for multiple datasets, use stable distinguishable names such as `京东_价格历史.xlsx`, “JD price history”). If Excel has the file open and locked, retain the pending synchronization; do not forcibly close the application.
4. Write the latest cloud version/hash and synced_at into the manifest, then read back the path and file. On failure, preserve the last good version and report pending status; the cloud master is unaffected.
5. Update only the latest mirror for the relevant dataset. Never delete Excel history as part of image cleanup. Handle additional CSV/source-data exports separately when requested.

## Generate Charts Only When Requested
Read the spreadsheet/charting skills if available in the environment and use the latest COMMITTED data. By default, produce the applicable set for which data exists and the chart is meaningful:
- `单品价格趋势.png` (“Single-item price trends”): comparable single-item totals at their original quantities; facet/paginate when there are many SKUs. Label unit prices separately and clearly to avoid overlapping incomparable series.
- `组合价格趋势.png` (“Combination price trends”): actual quotes for explicitly specified combinations; do not fabricate an empty trend where there are no observations.
- `组合历史估算.png` (“Estimated historical combination prices”): only when the request includes historical combination estimation and it is computable. Use solid lines for observations, dashed lines for estimates, separate scenarios for assumptions, and an explicit legend.
- `采集完整性.png` (“Capture completeness”): scheduled/successful/missing slots and coverage, exposing blind spots.
Add `价格与优惠变化.png` (“Price and promotion changes”) when needed; do not manufacture meaningless views just to increase the chart count. Specific user requests override the default selection. Separate different time windows/currencies/quantities. Use fonts and labels appropriate to the user's language (including Chinese-capable fonts for Chinese users); clearly show RMB units where applicable, timezone, latest observation, and missing-data markers.
Use a point plot for one point; with two points, state that there are only two observations rather than overstating a trend. With no data, provide only status/missing-data explanations. Do not connect gaps as if they demonstrated continuous stability, and do not impute by default. Mark only evidence-supported changes on promotion timelines.

## Publishing Images and Cleaning Up Old Charts
A request to draw charts includes publishing this batch to the already authorized and verified local image folder when the computer is online. It does not simultaneously trigger Excel synchronization; that still requires an explicit renew/synchronization request.

First generate the full batch in the cloud/a controlled temporary directory. Verify that each chart opens, is nonempty, and has correct dimensions, fonts, axes, labels, and correspondence to the data. Retain a new image manifest and source commit_id. If the user's computer is offline, keep the latest cloud charts and pending synchronization status; do not falsely claim they are already on the desktop.
When local writing is available, use compensatable publication: write and verify new temporary images → preserve recoverable backups of the old images and old manifest plus a publication log → atomically replace the corresponding images → atomically update the manifest → read back and verify consistency between new images and manifest → only after successful commit, move to the system Recycle Bin/Trash the backups of images replaced in this operation that were registered in the old manifest and matched its hashes. If any step fails, restore the old images and old manifest from backups and verify that a usable latest version remains. If restoration also fails, preserve all backups/logs and report exact paths and states; do not continue cleanup. If a platform only allows moving to Trash before publication, first confirm recoverability and record recovery locations; restore immediately on publication failure. A partial failure must not leave an empty directory with no usable charts. Clean up only old versions of the same chart role: redrawing only single-item charts must not remove combination charts that were not redrawn. If new charts fail, do not clean up old ones. Preserve user-modified charts and unregistered files and report conflicts.
If the environment lacks safe Recycle Bin/Trash support, retain the old images and report that cleanup remains pending; do not fall back to permanent deletion. If a new target filename collides with an unknown existing file, use a safe new name rather than overwriting a user file. Permission to use the Recycle Bin/Trash is not permission to empty it automatically or without limit; mention capacity if needed, but do not empty it yourself.
“重新画图” (“redraw the charts”) authorizes this update of the corresponding old skill-managed images, not deletion of the entire image directory. Prefer simple, understandable filenames; facets may use `单品价格趋势_01.png` (“Single-item price trends_01”). Removing facets no longer needed in this batch also requires that they be within the old manifest's scope and that the complete new set has succeeded first.
Each report must identify chart types, data cutoff time, and the distinction between observations and estimates, and separately state whether cloud completion and local synchronization succeeded.

Use stable cloud image identities registered by dataset_id + chart role as well, preferring replacement of the current version rather than creating unlimited new Library objects on every run. If new charts fail, retain the last good version. Recycle obsolete skill-owned cloud images only when the platform supports recoverable deletion and permissions allow it. Manage version history under the service's retention policy and quotas; do not promise unlimited versions or zero storage use. When capacity approaches a limit, report it and propose archival/retention options. Do not permanently delete, empty Trash, or clean up other people's files.

## Automatic transfer first, verified ZIP fallback
Do not start by asking the user to download or extract files. On an explicit sync request (and chart delivery within its granted scope), first try supported automatic transfer to the authorized connected computer. Resolve the actual Desktop and current destination. Read the current official transfer/Library instructions. Do not patch a signed/official transfer helper, disable metadata checks, or bypass a denial when an OS-specific feature (for example xattr) is unavailable. A normal unsupported capability failure permits a supported manual-download fallback; a denied access action does not authorize another access route.
If automatic transfer cannot finish, prepare a ZIP from the latest COMMITTED requested workbook and authorized charts. Keep `data/` and `image/` separate, plus a JSON manifest containing relative paths, roles, byte sizes, SHA-256 values, source commit, timestamps, and format version. Exclude secrets, account details, unrelated files, and source JSON unless requested. Give the package itself a SHA-256 outside the ZIP as trusted transfer metadata. Verify archive contents and hashes before attaching it natively in the user's conversation. State only the remaining user step: download this ZIP; the assistant/local Codex handles the rest. Do not call an accepted attachment send successful local sync.
After download or on the next authorized local connection, have local Codex locate the exact ZIP in Downloads/the user-designated path. A missing download toast is not failure: inspect candidate file names, including browser-added suffixes, and verify size/hash. Do not repeatedly download or choose by name alone. If inaccessible or absent, ask for only its location/download; preserve pending state.
Use ordinary local CLI/filesystem tools to inspect and extract into a new staging directory. Reject absolute/drive/UNC paths, `..` traversal, duplicate normalized/case-colliding paths, symlinks/hardlinks, unexpected executable files, and excessive expanded size/compression ratio. Enforce manifest allowlisted members and sizes; resolve every target inside staging, then check SHA-256. Never execute archive content. Validate workbook reopening/latest run and chart readability, then apply the earlier manifest-based atomic publication to verified Desktop/Price tracking/data and image. Preserve unknown or user-edited files with conflict copies; never indiscriminately overwrite a folder. Reopen destination files, verify final hashes, update manifest and report actual paths. Failure keeps the last usable copies and pending status; do not mark a manual download as completed extraction/synchronization.

## Cloud retention after chart delivery
Keep the authoritative Excel, source JSON, commit/recovery records, and required backups. They are never chart-cleanup targets. When the user has authorized cleanup after delivery, recoverably trash only skill-owned chart artifacts whose delivery has been verified and whose remaining chart/local-sync consumers are complete. “Send accepted” is not “delivered”; use a delivery result, verified recipient-accessible durable copy, or user confirmation. If no confirmation is available, retain pending artifacts without repetitive requests. Do not break a native attachment that still depends on the cloud object, or delete the only available image while a ZIP/local sync is pending. A retained verified delivered ZIP/local copy can satisfy the consumer requirement only when it is independently usable and does not depend on the object being removed.
Track artifact ID/path, owner, hash, role, delivery evidence, pending consumers, and recoverable deletion result. Regenerate future charts from preserved data when needed. If safe recoverable removal is unavailable, report cleanup pending, not permission to permanently delete. Permanent deletion or emptying Trash requires the current policy's separate action-time approval. This post-delivery policy complements, rather than replaces, the old-chart transactional replacement rules above.
