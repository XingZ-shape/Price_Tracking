# Scheduling, Errors, and Recovery

## Activation
Support `elapsed_interval` (every N hours measured as elapsed time from an explicit UTC anchor; N > 0), `daily_local` (one specified local time each day), and `wall_clock_times` (a user-specified list of local times). If no initial preference exists, explicitly present the default of every 4 hours using elapsed_interval; do not silently equate this with 00/04/08/12/16/20. Preserve wall_clock_times if the user has already chosen those six fixed Beijing-time slots. For daily collection without a specified time, suggest 10:00 as part of the initial bundled confirmation. Verify that the scheduler supports the chosen interval, timezone, and constraints; if not, explain and let the user choose a supported option. Do not pretend success or change the frequency unilaterally.
Default the timezone policy to `follow_user`, with `fixed` available. Prefer the user's current trusted IANA timezone setting or an explicitly named timezone (北京时间, Beijing time → Asia/Shanghai); record its source and verification time. The cloud environment's UTC timezone is not the user's timezone. A UTC offset alone cannot identify an IANA timezone, daylight saving rules, or travel; ask the minimum necessary question. Configure a fixed offset without daylight saving only if the user explicitly requests that, and label it accordingly. On each wake, check the latest available reliable user-timezone signal; when offline or without a new reliable signal, retain the last verified value. Do not claim real-time travel detection.
For wall-clock schedules, default to skipping nonexistent times during a daylight-saving gap and recording the reason; during a repeated time, run only on its first occurrence (record UTC/offset). Present this policy at initial configuration. If the tool cannot enforce it, do not enable that schedule. A timezone change must not shift an elapsed_interval UTC anchor; only its display and the local time of independent reminders change. Never automatically change the shopping site, delivery region, currency, or membership context because the timezone changes.
For frequency/timezone changes, create a schedule_revision under the dataset lock (old/new configuration, source, effective_from_utc, schedule anchor, DST policy, and read-back evidence); update the original task rather than creating a duplicate. Prepare, switch, and verify by reading back before marking the revision effective. Retain the original effective revision only when failure definitively occurred before any write. If a write occurred or its outcome is uncertain and read-back fails, mark the transition UNKNOWN/PENDING; do not claim either the old or new schedule is effective. First recheck the actual state of the same task, then reconcile configuration/retry. Claim restoration of the old schedule only after rollback and verified read-back; never create a duplicate task. If the tool cannot switch atomically, record the transition boundary and old/new task states, and use unique UTC scheduled instances and a lock to reject double triggers. Apply the same deduplication gate during an unknown transition; do not claim an unverified schedule is reliable. Do not claim timezone following has taken effect until read-back verification succeeds. Do not rewrite earlier runs or their original timestamps.
First locate any existing task for the dataset_id and update it instead of creating a duplicate. Save verified cloud data identities, configuration, context location, execution permissions, and the notification conversation into a real task. Read back its frequency, timezone, enabled state, and next_run when the tool exposes it; record task_id. If next_run is not exposed, save the explicit schedule and report an “estimated first occurrence according to the schedule, pending verification by an actual run”; do not fabricate a scheduler-returned value. Disclose when the scheduler does not support a persistent browser or required permissions. Saving a prompt is not proof that the task can actually run.
Enable after the first trial capture and user acceptance. During operation, both scheduler and browser run in the cloud; shutting down the user's computer affects only local synchronization. Cloud session expiry/service interruptions can still cause gaps; do not promise unconditional 24/7 operation.

## Idempotency and Concurrency
Derive run_id stably from dataset_id + scheduler_instance_id (or the scheduled UTC time); use a separate UUID for a manual run. Retries of one run have different attempt_id values but the same run_id. Include owner, acquired_at, lease_expiry, and a heartbeat in the lock. Verify that its owner has finished before taking over an expired lock; time expiry alone is not permission to take over an active UI operation.
Check committed runs first: return directly for an already successful run; repair a partial commit first; for a failed run, append attempt results and resume under the same run without deleting failure records. Preserve every distinct real time slot even when prices are identical. If a run overruns into the next scheduled slot, record SKIPPED_CONCURRENT for the next run rather than opening concurrent selection operations. Do not present the earlier run's actual time as the next slot's time.
Record missed slots as MISSING_RUN/in the run log with a reason. On the next run, observe only the present; never backfill historical slots with current prices.

## Error Classification and Actions
| Observed fact | Status/action | User-facing explanation |
|---|---|---|
| Tool connection unavailable | ENVIRONMENT_UNAVAILABLE; retain the failed run | The cloud browser is currently unavailable; no prices were read |
| Tool security policy refuses access before the page | TOOL_POLICY_DENIED; stop this path | The tool refused access; the website page has not been observed. Do not infer server location or website anti-abuse controls |
| Website displays an ordinary CAPTCHA/verification page | SITE_CHALLENGE; follow existing approval and current policy for limited normal-UI completion; stop on sustained failure or required user-device action | Report only a remaining blocker and the minimal needed step |
| Page session has expired | LOGIN_REQUIRED; do not read credentials | The session has expired; login is required again |
| Page readable but fields/coverage incomplete | PARTIAL/PARSING_FAILED; save observed facts | Coverage/fields are incomplete; this is not evidence of an empty cart |
| Temporary network error | NETWORK_ERROR; allow one bounded normal retry, then recheck login | This run did not finish due to the network; current prices cannot be guaranteed |
| Original selection cannot be restored | RESTORE_FAILED; stop further UI mutations | List the unrestored scope; do not claim restoration |
| User operates the same page | USER_CONFLICT; stop to avoid overwriting their state | Stopped to avoid a conflict; restoration is unverified |
| Save failure/version conflict | SAVE_FAILED/PARTIAL_COMMIT; preserve pending data | Data has not yet been reliably committed; do not call the run complete |

Explicitly record action, target, reason, attempted_at, and observation/evidence. A tool refusal does not mean the website refused access. Do not switch VPNs/proxies, use private windows/another account to bypass restrictions, extract Cookies, or use private interfaces to evade them. If page layout changes, reread its semantics normally and repair within non-destructive bounds; never blindly click historical coordinates.
When the same blocker persists across successive runs, briefly ask whether the user wants to pause to avoid repeated ineffective runs; do not pause without authorization. Pause/resume/cancel only this dataset's actual task and verify by read-back. Do not affect other tasks; cancellation does not delete history.

## Notifications
Default to a brief report after each run unless the user has configured a different preference: actual time; total cart row count (Unknown when unknown); successful/selectable quote counts; main comparable price and promotion changes; cloud Excel save status; exceptions; and selection restoration. Report even when nothing changed but a complete snapshot was saved. If only wording changes were observed, call them wording changes rather than inferring an actual promotion change.
Default chart reminders to **once every 3 days, regardless of the amount of new data**. Explain and confirm this at onboarding; the user may disable/pause them. Check when due through the scheduled cycle or an existing capture task. Starting from the formal activation anchor, remind every 3 calendar days during daytime in the user's timezone (suggest 10:00, confirmed initially or chosen by the user); record anchor/timezone/local_time. Prefer checking due reminders within the existing capture task: if captures do not occur at 10:00, remind on the first run after the due point and state the actual time. Create a separate reminder task only if the user requires an exact reminder time. Use only one approach to avoid duplicate reminders. Deduplicate by reminder_period_id: do not send twice for the same period, but do not suppress all future agreed periods indefinitely because the previous reminder went unanswered. Ask only “Would you like me to plot trends from the data available so far?” (Chinese alias: “需要我根据目前数据画趋势图吗？”), without generating charts. If data is insufficient, also explain that observation points/missingness can be plotted. Disabling reminders does not cancel collection.

## Configuration Changes and Repeated Blockers
Use dataset_id + stable scheduler instance, or a normalized scheduled UTC time, for run_id. Configuration version is an attribute of the record; changing a schedule must not execute the same logical instance twice. Deduplicate at the transition boundary while retaining distinct real UTC instances separately. If run duration exceeds the interval, record SKIPPED_CONCURRENT and ongoing duration/coverage warnings, and offer lower frequency or a narrower authorized combination scope. Without the user's decision, do not silently reduce frequency, create another task, or weaken safety checks.
The three-day chart reminder is an independent user preference and does not change with capture frequency. Under follow_user, reschedule only unsent reminders in the new timezone. Retain the stable period sequence/last_sent and original anchor; crossing dates/timezones must not resend the same period. After being offline across multiple periods, send only one currently due reminder and log skipped periods rather than flooding the user with catch-up messages. Remind even without new data; disabling reminders does not affect collection.
For persistent login/CAPTCHA blockers, retain only one currently valid request for user action. Continue logging each failed attempt, report briefly according to notification settings, and ask whether to pause; do not repeatedly send verification codes or open login flows. Once the user completes authentication, verify the actual page and clear stale waits. Do not stop the task without pause authorization. Stopping the current UI path is not the same as stopping the ongoing scheduled task.

For a quote-selection rollback, record SELECTION_ROLLBACK/RESTORE_FAILED as observed, stop subsequent mutations, retain successful partial data, and follow capture.md. Do not relabel an empty footer as whole-cart price or restart blindly at the next scheduled wake. Pending approval remains pending regardless of elapsed time. Existing user CAPTCHA grants can remove redundant questions but cannot override tool restrictions or mandatory action-time approval.
